brockmann-grid-system

A grid you can't measure is a mood board, not a system. This skill builds an editorial page on a real modular grid, then proves it at 0px.

skills/design/brockmann-grid-system scripts: grid_tokens.py · verify_grid.js

What it does

The skill encodes Josef Müller-Brockmann's grid discipline and the front-end engineering that makes the grid real on the web. It gives you three things:

  • The discipline. A modular grid of columns and rows, an 8px baseline, a grotesque sans, flush-left type, and large jumps in scale.
  • The engineering. One set of CSS variables, subgrid bands that place every element by column line, a baseline lock, and runtime optical alignment.
  • The proof. A scaffold generator (scripts/grid_tokens.py) and a Puppeteer harness (scripts/verify_grid.js) that measures adherence.

The skill has two hard limits. It does not change colours, and it does not draw a visible grid overlay or a show/hide-grid control. It governs layout, columns and vertical rhythm only.

Prerequisites

  • Python 3 to run scripts/grid_tokens.py. It needs no network and no credentials.
  • Node.js, puppeteer-core and Chrome to run scripts/verify_grid.js. Set CHROME to the Chrome binary and PUP to the puppeteer-core module path.
  • The real webfont as a local TTF if you want to verify optical alignment offline. See the warning below.

How it works

The skill follows a fixed workflow. You build first, then you measure, and you fix until the harness passes.

  1. Pick the subject. Gather real photos and host them publicly.
  2. Generate the scaffold. Run python3 scripts/grid_tokens.py, or add --scaffold for a full page. Wire it into the page's existing palette.
  3. Build the spreads. Place every element by column line inside a band. Lock spacing, line-heights and media heights to the baseline.
  4. Add optical alignment. The scaffold already has the JS. Point its selector list at your display elements.
  5. Verify. Run the harness, look at a zoom crop of the top-left corner, fix and run again.

One source of truth

Every grid parameter lives in :root CSS variables: --cols, --gutter, --margin, --bl (baseline), --lh (leading, 3 × baseline) and --maxw. Every element reads the same variables, so placements stay consistent at every viewport width.

Subgrid bands

A band spans all columns and exposes them again as a subgrid. Children place with grid-column: <startline> / <endline>, for example 1 / 6 and 6 / 13. You never eyeball a span.

Baseline lock

  • Every line-height is a multiple of the baseline. Use px for display type, not unitless values.
  • Every margin and padding is a multiple of the baseline.
  • Media heights are multiples of the leading (for example 240, 360, 432 or 480px), so the top and bottom of a photo land on lines.

Optical alignment

A large headline can have its box exactly on a column line and still look wrong. The letterform's ink is inset by its left side-bearing. Box-on-grid is not ink-on-grid.

The runtime JS measures the first glyph with canvas actualBoundingBoxLeft and shifts the element so the ink lands on the line. It runs after document.fonts.ready and on resize, so it uses the font that actually loaded.

Side-bearing is font-specific

Headless Chrome often lacks the webfont and falls back to another grotesque. The skill measured −16px on the fallback and −7px on real Inter for the same H. To verify optics offline, embed the real webfont with @font-face.

The three checks

verify_grid.js renders the page at several widths, above and below --maxw (default 1440,1180,900). At each width it checks:

  1. Column adherence. Each .band > * starts on a column start line and ends on a column end line. The harness builds both sets, so a span that ends past a gutter does not report a false error. It skips the optically aligned display elements.
  2. Baseline. Text tops, modulo the baseline, are close to 0. It measures per spread, against that spread's .grid top.
  3. Optical ink. Each display element's ink-left equals its own nearest column start, not always line 1.

What you get

CommandOutput
python3 scripts/grid_tokens.pyA block on stdout: :root tokens, the .grid/.band CSS, the optical-alignment JS and a band markup pattern
python3 scripts/grid_tokens.py --scaffoldA full minimal HTML page with the same block
--cols --baseline --gutter --margin --maxwCustom grid values. Defaults are 12, 8, 24, 72 and 1296. It warns if gutter or margin is not a baseline multiple.
node scripts/verify_grid.js <file-or-url>One [PASS] or [FAIL] line per width, then GRID VERIFY: PASS, or GRID VERIFY: FAIL with exit code 1

The scaffold emits no colours. A band from the scaffold looks like this:

.band {
  grid-column: 1 / -1;
  display: grid;
  grid-template-columns: subgrid;
  column-gap: var(--gutter);
  align-items: start;
}
@supports not (grid-template-columns: subgrid) {
  .band {
    grid-template-columns: repeat(var(--cols), 1fr);
  }
}

To verify, run the harness with the two environment variables set:

CHROME=/path/to/chrome PUP=/path/to/puppeteer-core \
  node scripts/verify_grid.js file:///path/to/index.html --widths=1440,1180,900

A clean run reports col=0px baseline≤4px ink=0px and ends with GRID VERIFY: PASS.

Common questions

Will it change my page's colours?
No. The skill sets no palette tokens and no background or color rules. It keeps the host design system's colours exactly as they are.
Can I turn on a grid overlay to check alignment by eye?
No. The skill does not draw a visible grid or a toggle. The harness proves the grid by measurement, and a top-left zoom crop is the human check.
Why does my headline look off the grid when its box is on it?
Large glyphs have a left side-bearing, so the ink sits inside the box. The optical-alignment JS shifts the element so the ink, not the box, lands on the line.
Why does the optical check fail in headless Chrome but look fine in my browser?
Headless Chrome probably used a fallback font with a different side-bearing. Embed the real webfont through @font-face with a local TTF, then run the check again.
Why test at widths above and below the max-width?
A centred container can drift when the viewport is wider or narrower than --maxw. Several widths catch that drift.
Which grid should I start with?
For the web, a 12-column grid with an 8px baseline is a strong default. Use a 6×6 or 4×8 modular field grid when you want visible rows too.

It’s working if

  • verify_grid.js prints GRID VERIFY: PASS at every width you test.
  • Each width line shows column error ≤ 0.5px, baseline error ≤ half a baseline, and ink error ≤ 1px.
  • In a top-left zoom crop, the masthead ink, the body text and the column line share one edge.
  • The page's colours are the same as before the skill ran.
  • Every grid value comes from the :root variables, not from numbers on single elements.

Where it fits

brockmann-grid-system sits between a page's content and its final layout. Use it after you have the words and photos, and before you publish.

content + photos → grid_tokens.py scaffold → subgrid bands + optical JS → verify_grid.js → PASS → publish

To write the copy first, use write-doc. To polish it, use quill-edit. For a Vignelli Canon layout, use the sibling Vignelli Canon skill instead.
