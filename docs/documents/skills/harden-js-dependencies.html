harden-js-dependencies

Make new package versions wait before they reach your repo. Most bad releases are found and removed in hours, so a 7-day wait keeps them out.

skills/work/harden-js-dependencies npm · bun · pnpm · yarn default: 7 days

What it does

The skill sets an install cooldown for your project. With a cooldown, a package version must be public for N days before your package manager will install it. The default is 7 days.

It finds your package manager, checks that its version supports a cooldown, and writes one key to the correct config file. It writes for one package manager only.

Be clear about the limit. This is one control, not a security program. It does not stop a package that was already malicious a month ago, or a version that you pin yourself.

Prerequisites

Each tool ignores unknown config keys with no warning. On an old version, the file looks safe and does nothing. So the skill checks the version first.

ManagerCheckMinimum version
npmnpm --version11.10.0
bunbun --version1.3
pnpmpnpm --version10.16
yarnyarn --version4.10.0
Too old means no file

If your version is below the minimum, the skill does not write the config. It tells you the version you have and the version you need. You decide if you upgrade first.

How it works

  1. Detect. The skill reads the packageManager field in package.json first. If there is none, it looks at the lockfile: bun.lock or bun.lockb, pnpm-lock.yaml, yarn.lock, package-lock.json. With no lockfile or more than one, it asks you and stops.
  2. Check the version. It runs the version command and compares the result with the minimum.
  3. Write. It writes the cooldown key in the format and unit of that tool. If the file exists, it edits only the cooldown key and keeps every other line.
  4. Offer excludes. It tells you that you can exempt packages, for example your own internal ones. It adds an exclude only when you name the package or scope.
  5. Report. It tells you the file path, the key, the value and its unit, and the manager and version. Then it flags what you will notice next.
Why only one file

A stray .npmrc in a bun repo makes the next reader think the repo has protection. So the skill writes only for the manager it detected.

What it writes

Each tool uses a different key and a different unit. The skill never copies a value from one tool to another without converting it.

ManagerFileKeyUnit7 days
npm.npmrcmin-release-agedays7
bunbunfig.tomlminimumReleaseAge under [install]seconds604800
pnpmpnpm-workspace.yamlminimumReleaseAgeminutes10080
yarn.yarnrc.ymlnpmMinimalAgeGateminutes or a duration string"7d"

The exclude keys are minimumReleaseAgeExcludes (bun, an array under [install]), minimumReleaseAgeExclude (pnpm, a list) and npmPreapprovedPackages (yarn, a list). npm has no exclude support.

For npm:

# Don't install package versions published less than 7 days ago.
min-release-age=7

For bun:

[install]
# Don't install package versions published less than 7 days ago.
minimumReleaseAge = 604800

For pnpm:

# Don't install package versions published less than 7 days ago.
minimumReleaseAge: 10080

For yarn:

# Don't install package versions published less than 7 days ago.
npmMinimalAgeGate: "7d"

These files often hold registry URLs and auth tokens. That is why the skill edits in place and never overwrites the whole file.

Common questions

Why 7 days?
Most npm supply-chain compromises are found and unpublished within hours. A 7-day wait lets that window pass before the version can reach your repo.
I already have a cooldown with a different value. Will it change it?
Not without asking. The skill shows you the current value and asks what you want.
A new release I need is blocked. What do I do?
That is the cooldown working. Add the package to the exclude list, or use a temporary flag. Do not delete the config.
Can I exempt our internal packages on npm?
No. npm has no exclude support. bun, pnpm and yarn each have an exclude key.
Why didn’t it write a file for my repo?
Either your package manager is below the minimum version, or it found no lockfile or more than one. In both cases it tells you why and stops.
Does this protect me from all malicious packages?
No. It only blocks versions that are newer than the cooldown. An old malicious package, or a version you pin yourself, still installs.

It’s working if

  • Only one config file changed, and it matches your package manager.
  • The value uses the correct unit for that tool, for example 10080 minutes for pnpm.
  • Every other line in the existing file is the same as before.
  • The file is committed and not in .gitignore, so CI uses the same cooldown.
  • An install of a version published today fails until the cooldown passes.

Where it fits

Use this skill when you set up a JavaScript repo, or once on a repo that you already have. After that, the cooldown works on every install, locally and in CI.

JS repo → harden-js-dependencies → config file committed → installs wait 7 days
release blocked → add exclude (bun / pnpm / yarn) → install

CI must use the same config. If the file is not committed, or CI overrides it, the protection is local only. For other guardrails, see git-guardrails-claude-code and security-review.
