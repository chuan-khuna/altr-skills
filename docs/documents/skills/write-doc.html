write-doc

Synthesise, don't transcribe. The skill turns a conversation or a codebase feature into a markdown document that a reader understands on its own.

skills/productivity/write-doc modes: conversation · explore

What it does

write-doc has two modes. Both modes end with one markdown file, written only after you confirm the path.

  • Mode 1, conversation to doc. The skill extracts the context, key decisions, outcomes and open questions from the current chat. It does not copy the back-and-forth.
  • Mode 2, explore and document. The skill investigates a feature in the codebase, then writes technical documentation about how it works.

The skill detects the mode from your words. If it can't tell, it asks one question: “Should I document this conversation, or explore a feature in the codebase?”

Do not start it before there is a conversation, or before you name the feature. In both cases the skill stops and asks.

How it works

The two modes collect material in different ways. Then they share the same draft-and-save flow.

Mode 1: conversation to doc

  1. Extract. The skill pulls out four things: context, key decisions and why, outcomes, and open questions.
  2. Write standalone. A reader who was not in the conversation must understand the doc.
  3. Add a diagram if it helps. If the chat covered a design, flow or architecture, the skill adds a Mermaid diagram. It skips the diagram for discussion with no structure.

Mode 2: explore and document

  1. Ask. The skill asks two questions in one message: what depth (overview or deep detail) and what scope (what to focus on or exclude). It waits for your answers. If your trigger already answers them, it continues.
  2. Explore. It uses grep, glob and file reads to trace code paths, key modules, data flow and edge cases.
  3. Write. It uses the default sections below and adds at least one Mermaid diagram when the feature has real structure.
SectionInclude when
OverviewAlways. One paragraph: what, why, and where it fits.
How It WorksAlways. The core mechanism, end to end.
Request / ResponseThe feature has an API or protocol boundary.
Key Files / Entry PointsThe codebase is non-trivial.
Usage / ExamplesThe feature has a public API or other code calls it.
Notes / CaveatsThere are gotchas worth saving the next engineer from.

Draft and save (both modes)

  1. Show the draft in chat as one block. Nothing is on disk yet.
  2. Take one round of revisions. The skill applies your changes at once.
  3. Propose a filename and path. It waits for you to confirm.
  4. Write the file only after you confirm. It never overwrites a file without your permission.
Three revisions is a smell

One revision is normal. If you get to three, the skill stops guessing and asks which section is wrong.

The skill infers <category> from the content, for example prd, adr, issues, auth, api or architecture. The <topic> is kebab-case, 2 to 5 words. A mode 2 doc for a sign-in API starts like this:

# JWT Sign-In API

## Overview
When the frontend sign-in page submits credentials, it calls `POST /api/auth/sign-in/`.
Django REST Framework validates the credentials, then returns an access token and a refresh token.

## How It Works
(sequenceDiagram: Browser → DRF → Database, then Bearer token on later requests)

## Key Files / Entry Points
- `urls.py` — registers `POST /api/auth/sign-in/` → `SignInView`
- `settings.py` — `SIMPLE_JWT` block controls token lifetimes

The skill saves it as, for example, docs/artifacts/auth/2026-05-23-jwt-sign-in-api.md.

Common questions

Will it save the chat word for word?
No. It synthesises decisions, mechanisms and outcomes. If you want a raw transcript, the skill asks you to clarify before it continues.
Why does it ask about depth and scope before it explores?
An overview and a deep technical doc need different exploration. Two answers up front keep the skill from tracing code you don't care about.
Does it always add a diagram?
No. It adds a Mermaid diagram only when there is structure to show, such as a flow, a state machine or service interactions.
Can it overwrite an existing doc?
Only with your explicit permission. It also never writes anything before you confirm the full path and filename.
What if the code is unclear?
The skill never invents facts. It marks the gap clearly instead of filling it with a guess.

It’s working if

  • Someone who missed the conversation can read the doc and know what was decided and why.
  • A mode 2 doc names real files, functions and field names, not “some module”.
  • Every doc has an Overview and a How It Works section.
  • No file appears on disk before you confirm the path.
  • You approve the draft after one round of revisions, not three.

Where it fits

write-doc sits at the end of a discussion or an investigation. Use it when the thinking is done and you want a record that lasts.

design chat      → write-doc (mode 1) → draft → confirm path → docs/artifacts/adr/…md
"how does X work" → write-doc (mode 2) → explore → draft → confirm path → docs/artifacts/<domain>/…md

To turn a doc into work for someone else, use calm-down assign. To polish the prose, run quill-edit on it. For notes from reading material, use evergreen-note-writer.
