technical-writing

A writing standard in four layers, so a tired engineer understands your doc on the first read.

skills/writing/technical-writing manual only

What it does

technical-writing is a set of rules that Claude applies when it writes or reviews docs, RFCs, READMEs, PR descriptions or commit messages. The rules come in four layers. Each layer works at a smaller scale than the one before:

  1. Diátaxis picks the mode of the whole document.
  2. Google developer style shapes each sentence for the reader.
  3. STE rules make each statement load one at a time.
  4. Global English leaves no sentence open to two readings.

Over all four sit a few base rules. Cut every word that does no work. Use the short, everyday word: “use”, not “utilize”. Write the real symbol, file, flag or command name. If a rule makes a sentence worse, fix the sentence another way or leave it alone.

The skill comes from cursor/plugins pstack, pinned at commit e1cc031.

How it works

  1. Pick the mode. One document has one mode: tutorial, how-to, reference or explanation. If a doc mixes modes, split it and link the parts. Opinion belongs only in explanation.
  2. Write to the reader. Use “you” and the present tense. Write instructions as commands, with the condition first. Never write “simply”, “easy” or “quickly” in a procedure. Headings carry the point, in sentence case.
  3. Load one statement at a time. One instruction per sentence. Split instructions over about 20 words and other sentences over about 25. Put the warning before the step it guards.
  4. Remove second readings. Keep “only” and “not” next to the word they change. Make every “it”, “they” and “this” point at one thing. Use periods, not semicolons or em dashes. Skip idioms and Latin abbreviations.
  5. Apply unslop. The skill hands the slop-pattern catalogue to unslop for every doc it touches.

Rules for PRs and commits

PR descriptions and commit messages are writing too. Every layer except Diátaxis applies to them. A PR body is a briefing that a reviewer reads in under a minute. Link logs and metric tables. Do not paste them.

What it writes

The skill writes no file of its own. It changes how Claude writes the doc, PR description or commit message you asked for. Two examples of the change:

Before: Schema changes can cause issues, so simply run the migration first.
After:  A column rename fails the build. Run the migration first.

Before: It is important to note that the cache, which is optional, should be utilized.
After:  Use the cache. It is optional.

Common questions

Does it apply to UI strings in my product?
No. Product UI strings are not documentation. Use your product's copy guidelines for those.
What if a rule makes the sentence worse?
Fix the sentence another way, or leave it alone. The rules serve the reader, not the other way round.
Why no semicolons or em dashes?
The Global English layer prefers periods. A reader who does not speak English as a first language parses two short sentences more easily than one joined sentence.
Is opinion allowed?
Only in explanation. Tutorials, how-to guides and reference stay neutral.

It’s working if

  • Each document is one mode: tutorial, how-to, reference or explanation.
  • Procedures are numbered commands, one instruction per sentence.
  • The text names real files, flags and commands, in code font.
  • Every “it” and “this” points at one obvious thing.
  • A PR description reads in under a minute.

Where it fits
